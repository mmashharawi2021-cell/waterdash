# WaterDash Authentication and Authorization Security Map

## Scope and evidence

This is a read-only source audit of commit `44bc81b6e3a67030f190a6a148d9cd82b645007c`. It does not inspect or invoke Firebase production services.

## Current identity and session model

| Flow | Current implementation | Security result |
| --- | --- | --- |
| LOGIN_FLOW | `App.login` calls `FirebaseService.signIn`. `assets/core-system.js` compares username/password with `WATER_APP_SETTINGS` in browser JS, then calls `signInAnonymously()`. | The Firebase identity is anonymous and browser JavaScript controls credential checking. |
| Alternate login | `AuthUsers.signIn` anonymously authenticates, reads a `users` document by `username`, browser-hashes the submitted password with SHA-256, and compares `passwordHash`. | Password verification and its database are exposed to an authenticated anonymous client. |
| SESSION_FLOW | Firebase restores the anonymous session. `AuthUsers.setCurrentUser` writes normalized role and permissions to `localStorage` key `waterAppCurrentUser`. | Client state can be modified and cannot authorize data access. |
| SESSION_RESTORE_FLOW | `AuthUsers.currentUser` prefers in-memory/localStorage state and falls back to a synthetic `local-default-admin` superAdmin for any Firebase-authenticated user. | An anonymous session can obtain a privileged UI identity. |
| LOGOUT_FLOW | `App.logout` invokes Firebase sign-out; `AuthUsers.signOut` clears localStorage first. | Logout exists, but client role state must not be used for authorization. |

## Existing user-record model

Observed `users` fields are `username`, `fullName`, `role`, `permissions`, `active`, `passwordHash`, `createdAt`, `updatedAt`, `createdBy`, and `lastLoginAt`. `passwordHash` is a browser-produced SHA-256 digest. New document IDs are generated by Firestore. No source path records a Firebase Auth UID or requires an email, and source does not prove username uniqueness.

The repository therefore cannot safely determine whether any production record maps to a Firebase Auth UID, has a usable email, or has a stable identity other than its document ID. No mapping may be fabricated; production inventory and human verification are required before cutover.

## User creation, password, and role flows

| Flow | Current implementation | Broken boundary |
| --- | --- | --- |
| USER_CREATION_FLOW | `AuthUsers.saveUser` writes caller-supplied `role`, `permissions`, `active`, and optional browser-created `passwordHash` to `users`. | Client supplies privilege-bearing fields. |
| PASSWORD_FLOW | `hashPassword` uses `crypto.subtle.digest('SHA-256')`; the unsalted digest is persisted and later compared in browser code. | Password verification is not performed by a trusted identity provider. |
| ROLE_ASSIGNMENT_FLOW | User UI submits role and permission controls to `saveUser`; Rules use `users/{request.auth.uid}.role`. | A caller can write a role document that Rules trust. |
| Disabled-user flow | UI records `active`; current Rules do not use it for reports, fuel, settings, or stations. | Disabling a record is not enforcement. |

## Firestore authorization flow

`firestore.rules` derives `getRole()` from `users/{request.auth.uid}.role` and uses the legacy string `admin` for administrative checks. The client uses a different privileged string, `superAdmin`. Rules allow any authenticated user to read all `users` documents and allow self create/update. The P0 source-to-sink attack is:

```text
anonymous Firebase session
  -> direct SDK write /users/<own-auth-uid> { role: "admin" }
  -> getRole() reads caller-writable document
  -> isAdmin() authorizes privileged Firestore operations
```

UI checks in `auth-system.js`, `ui-system.js`, and `fuel-system.js` are presentation guards only and can be bypassed by DevTools or direct SDK calls. The security boundary must be Firestore Rules backed by a value the caller cannot write.

## Other write paths

- `FirebaseService.saveReport`, `deleteReport`, `logActivity`, and `seedSettings` write Firestore from the browser.
- `App.start` invokes `seedSettings` after each authenticated session.
- Settings, stations, reports, fuel entries, activity logs, and users must therefore be secured by Rules, never client guards.

## Legacy classification

| Component | Classification | Cutover treatment |
| --- | --- | --- |
| `users` documents and `passwordHash` fields | MIGRATION_ONLY data | Preserve unchanged until post-cutover retention approval. |
| Browser SHA-256 comparison and anonymous login | DEPRECATED, unreferenced legacy file in candidate | Retain only as migration evidence; it is not loaded into the candidate runtime. |
| Browser role/permission state | UX-only display state | Never accepted by Firestore Rules. |
| `admin` Rules role | Rules-only legacy alias | Replace with canonical vocabulary; do not globally rename data. |

## Canonical RBAC vocabulary and permission matrix

`admin` is not a defined application role in `AuthUsers.ROLE_DEFINITIONS`; it is a Rules-only legacy alias. Canonical roles are `superAdmin`, `supervisor`, `dataEntry`, and `viewer`.

| Permission | superAdmin | supervisor | dataEntry | viewer |
| --- | :---: | :---: | :---: | :---: |
| VIEW_REPORT | yes | yes | yes | yes |
| CREATE_REPORT | yes | yes | yes | no |
| EDIT_REPORT | yes | yes | no | no |
| DELETE_REPORT | yes | no | no | no |
| VIEW_FUEL | yes | yes | yes | yes |
| ADD_FUEL | yes | yes | yes | no |
| EDIT_FUEL | yes | yes | no | no |
| DELETE_FUEL | yes | no | no | no |
| EXPORT_REPORTS | yes | yes | no | yes |
| MANAGE_USERS | trusted mechanism only | no | no | no |
| MANAGE_SETTINGS | yes | yes | no | no |
| MANAGE_STATIONS | yes | yes | no | no |

Exports are browser-generated from data the user may read; Rules secure the corresponding reads. “Trusted mechanism only” means Firebase Admin SDK or a trusted server outside the browser.

## Candidate security invariant

Firebase Authentication supplies identity. A signed ID-token custom claim, `waterdashRole`, supplies the canonical role. Only Firebase Admin SDK or a trusted server can issue/change that claim. Firestore Rules derive permissions exclusively from the token and never trust a role or permissions value from a caller-writable document.

`CLIENT_GUARD = UX`; `FIRESTORE_RULES = SECURITY_BOUNDARY`.
